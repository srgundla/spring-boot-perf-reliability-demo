Part B · Database efficiency

Deep pages: OFFSET discards rows, keyset seeks

OFFSET paging

ORDER BY id OFFSET 495000 LIMIT 5

  • Reads and throws away 495,000 rows
  • Spring Data’s Page adds a COUNT(*)
  • Cost grows with depth
  • Can jump to any page

Keyset paging

WHERE id > 495000 ORDER BY id LIMIT 5

  • Seeks straight into the primary-key index
  • No COUNT(*)
  • Cost stays flat at any depth
  • Only next and previous

Live: same five rows from both endpoints. Compare tookMs in the response.

Day of Data Orlando 2026

The products table has 500,000 rows. Show the shallow page first (page 1) so nobody thinks OFFSET is always bad, then page 99000. The ratio matters more than the absolute numbers on a laptop. Code: ProductRepository, findAllByOrderByIdAsc versus findNextPage. Trade-off to say out loud: keyset gives you next and previous, not page 7,000.

N+1: the same 20 orders, far fewer queries

≈21

SQL statements, lazy loading

One query for the orders, then one per order for its items.

2

SQL statements, fixed

Page over ids, then one JOIN FETCH for those ids.

At 200 orders it is ≈201 against 2. Each extra statement is a round trip to a real database.

Day of Data Orlando 2026

Run /orders/api/orders/slow?size=20 then /fast?size=20 and read sqlStatements, the first field in the response. Expect about 21 and 2; confirm the exact numbers live and change the slide if they differ. The fix is in two steps so pagination stays in SQL: JOIN FETCH on a collection combined with paging forces Hibernate to page in memory. Code: OrderQueryService and OrderRepository.

Part B · Database efficiency

Three more database habits

Short transactions

Never hold a connection while calling another service. place() is not transactional; only save() is.

Select what you need

An interface projection reads four columns, not the whole entity.

Do the pool math

20 connections × 3 replicas = 60 of PostgreSQL’s default 100. That is your scale-out ceiling.

Day of Data Orlando 2026

Three quick points, one sentence each. The transaction point is the one people forget: with open-in-view off and no class-level @Transactional, the connection is only checked out for the save. Pool math: Grafana shows active and pending connections; pending greater than zero is the first sign the database is the bottleneck.

Day of Data Orlando 2026

Honesty point first: a primary-key lookup on a laptop is about 1 ms, so the database path includes a 25 ms pg_sleep standing in for an expensive join or aggregation. Say that out loud. Then walk the four steps. The cache is cache-aside: the application owns the logic and PostgreSQL stays the source of truth. Code: ProductService.

Part C · Caching

Cache read-heavy, expensive, slowly changing data

TechniqueWhat it gives youWhat it costs
TTL of 120 sBounded staleness if an eviction is missedReads up to 2 minutes old
Evict on writeNew price shows on the next readEvery write path must evict
sync = trueOne database load per key, no stampedeOther callers wait briefly
Cache-asidePostgreSQL stays the source of truthApp code owns the logic

Redis is another service to run, size, monitor and keep consistent. Cache on purpose, not everywhere.

Day of Data Orlando 2026

sync=true is the stampede protection: when a thousand requests miss on the same key at the same moment, one goes to the database and the rest wait for its result. The TTL is a safety net for stale data, not the main invalidation strategy. Close with the cost line: a cache is not free.

Part D · Resilience

When the catalog gets slow, orders must not

Circuit breaker

Opens at 50% failures over 10 calls, then fails fast for 10 s

Bulkhead

At most 20 calls in flight to the catalog (@ConcurrencyLimit)

Retry

2 retries with backoff and jitter, only for timeouts and 5xx (@Retryable)

Timeouts

300 ms to connect, 800 ms to read: never wait forever

Fallback

Accept the order as PENDING_PRICE_CHECK and price it later

Day of Data Orlando 2026

Read the layers top to bottom in call order: the breaker wraps the bulkhead, which wraps the retry, which wraps the HTTP call with its timeouts. Retry and the concurrency limit are built into Spring Framework 7; Spring has no circuit breaker, so that one piece is the plain Resilience4j library. The fallback is a business decision, not a technical one: ask the business whether an order without a confirmed price is acceptable. Code: CatalogClient, CatalogHttp, CatalogBreaker.

Part D · Resilience

The circuit breaker has three states

CLOSED

Calls flow normally. Failures are counted over the last 10 calls.

50% or more fail

OPEN

Calls fail fast with no network use. Orders take the fallback.

After 10 seconds

HALF-OPEN

Three trial calls decide: all succeed, back to CLOSED; a failure, back to OPEN.

Grafana plots the state as a number: 0 closed, 1 open, 2 half-open.

Day of Data Orlando 2026

Short slide, set up the demo. The breaker converts a slow failure into a fast, predictable one. A 404 from the catalog does not count as a failure: that is the caller's mistake, not evidence the catalog is unhealthy. Settings and a unit test are in CatalogBreaker and CatalogBreakerTest.

2 · Open

Metrics tell you that. Traces tell you where.

Metrics

Micrometer, Prometheus, Grafana

  • Rate, errors and p95 latency
  • Connection pool pressure
  • Cache hit ratio
  • Breaker state and fallbacks

Traces

OpenTelemetry, Jaeger

  • One trace across both services
  • Each retry attempt as a span
  • The backoff gaps between them

Health probes

Spring Boot Actuator

  • Liveness: restart me if I am wedged
  • Readiness: send me traffic only when my dependencies are fine

Part E · Scale-out

Virtual threads lift the thread limit, so limit elsewhere

What changes

  • A blocked call parks a cheap virtual thread
  • No pool of 200 platform threads to exhaust
  • Java 25, one property to turn on

spring.threads.virtual.enabled=true

What you must add

  • @ConcurrencyLimit(20) on the catalog call
  • A capped connection pool: 20 per instance
  • A timeout on every remote call

Without limits, cheap threads just move the pile-up to the database.

Day of Data Orlando 2026

Two-minute talk-through while a load test runs; show the JVM live threads panel. Optional A/B: restart both services with VIRTUAL_THREADS=false (the runbook has the Mac and Windows syntax) and repeat. The point is not that virtual threads are faster for everything, it is that blocking code becomes cheap, and cheap threads need explicit limits somewhere else.

Part E · Scale-out

Scale out only works if services are stateless

What makes it work

  • No session state in memory
  • Config from environment variables
  • Readiness probe gates traffic
  • Graceful shutdown drains requests

Take it home

Seven habits for the next design review

1

Measure first: p95, errors, saturation

2

Count queries per request, fix N+1 before buying hardware

3

Cache expensive, read-heavy data with a TTL and eviction

4

Timeout every remote call, retry with backoff and jitter

5

Agree the degraded behaviour with the business first

6

Stay stateless, configure by environment, probe liveness and readiness

7

Test failure on purpose, not only success
